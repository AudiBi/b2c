# Sécurité

Décrit ce qui est **en place et testé**, puis ce qui **manque**. La revue de la phase 9 a pris l'OWASP ASVS niveau 2 comme **liste de contrôle** (voir « Revue de la phase 9 ») : ce document ne vaut ni audit externe ni certification.

## Mesures en place

| Domaine | Mesure | Où / test |
|---|---|---|
| Isolation des entreprises | `company_id` NOT NULL partout ; Row-Level Security activée **et forcée** sur 52 tables (celles qui portent `company_id`, plus `companies`) ; le rôle de l'API n'est ni superutilisateur, ni `BYPASSRLS`, ni propriétaire ; sans contexte, aucune ligne n'est visible ; contexte posé par `SET LOCAL` dans la transaction (pas de fuite entre requêtes sur le pool) ; clés étrangères composites (une session ne peut pas relier un utilisateur à une autre entreprise) | migration 0001, `DbService`, `rls.spec.ts` |
| Mode plateforme | Un seul drapeau (`app.platform`) ouvre la table `companies` ; il ne donne accès à aucune donnée métier ; seuls 2 fichiers peuvent l'utiliser (un test le vérifie en lisant le code source) | `iam.spec.ts` |
| Mots de passe | argon2id (mémoire 64 Mio par défaut, 3 itérations) ; longueur 10-128 ; liste de mots de passe courants (courte) ; refus si contenant l'adresse e-mail ; vérification factice pour les comptes inconnus (temps de réponse comparable) | `PasswordService`, `auth.spec.ts` |
| Sessions | jeton d'accès JWT HS256 15 min (algorithme, émetteur, audience imposés) ; droits relus en base à chaque requête ; jeton de renouvellement opaque (256 bits, seul le condensé SHA-256 est stocké) à rotation ; réutilisation = révocation de la famille ; cookie HttpOnly + SameSite=Lax + chemin restreint + en-tête anti-CSRF | `auth.spec.ts` |
| Jetons e-mail | 256 bits, condensés en base, usage unique atomique, durées 24 h / 1 h / 72 h, un nouveau jeton invalide les précédents | `auth.spec.ts` |
| Énumération de comptes | Inscription, renvoi de confirmation et mot de passe oublié répondent identiquement que le compte existe ou non ; connexion : même message pour mot de passe faux, compte inconnu et entreprise inconnue | `auth.spec.ts` |
| Force brute | 5 échecs → compte (même inexistant) verrouillé 15 min, quelle que soit l'IP ; limites par IP sur chaque route d'authentification ; envois d'e-mails limités par adresse | `rate-limit.spec.ts` |
| Autorisation | refus par défaut (une route sans règle est refusée) ; permissions vérifiées côté serveur avant la validation ; anti-escalade de privilèges ; protection du dernier administrateur avec verrou ; révocation immédiate (désactivation, suspension) | `iam.spec.ts` |
| Validation | schémas zod stricts partagés ; champs inconnus refusés (pas de mass assignment) ; requêtes SQL uniquement paramétrées (Prisma, gabarits `$queryRaw`) | `auth.spec.ts`, `iam.spec.ts` |
| Journal d'audit | écrit dans la transaction de l'action ; ajout seul (droits + déclencheur, même pour le propriétaire) ; IP, identifiant de requête, acteur ; clés sensibles masquées | `rls.spec.ts`, `app.spec.ts` |
| Erreurs | format unique ; aucune trace ni message interne dans les 500 | `app.spec.ts` |
| En-têtes et CORS | Helmet (HSTS, nosniff, CSP…), origines CORS en liste blanche, `X-Powered-By` retiré | `app.spec.ts` |
| Secrets | aucun dans le dépôt ; `.env` ignoré ; générés localement ; la configuration de production refuse les valeurs de substitution, les cookies non sécurisés et un coût argon2 trop faible | `app.spec.ts` |
| Site web | Jeton d'accès en mémoire (jamais dans localStorage ; un test le vérifie) ; cookie de renouvellement HttpOnly ; redirection après connexion limitée aux pages de l'espace client du même site ; CSP de référence sans script ni style en ligne (la recette navigateur échoue sur toute violation) ; liens externes en `rel=noopener` ; aucune donnée personnelle dans l'URL hormis les jetons à usage unique des e-mails | `e2e/` |
| Espace client | Chaque route ne manipule que les données de l'utilisateur du jeton ; l'identifiant d'un autre client donne 404 ; bénéficiaires : seuls 4 caractères de la pièce conservés ; entrepôts : le modèle d'adresse des clients n'est jamais public ; coordonnées publiques : URL `https` uniquement | `customers.spec.ts` |
| Colis et historique | Statut modifiable par un seul chemin (verrou de ligne, table de transitions, permission + portée d'entrepôt, motif) ; la base refuse tout changement de statut sans événement et toute modification de l'historique, même pour le propriétaire des tables ; un colis hors portée ou d'une autre entreprise est présenté comme inexistant | `packages.spec.ts` |
| Suivi public | Numéro à 50 bits aléatoires (secret) + caractère de contrôle ; recherche par fonction SQL `SECURITY DEFINER` qui ne renvoie que l'entreprise ; réponse 404 identique pour inconnu, mal formé ou contrôle erroné ; limite 30/min/IP, `no-store` ; **aucun** nom, téléphone, adresse, valeur, document, acteur ni texte libre ; motifs de retenue sensibles masqués | `packages.spec.ts`, `e2e/parcels.spec.ts` |
| Tarifs | Grille active immuable (API **et** déclencheurs) ; périodes sans chevauchement (contrainte d'exclusion) ; calcul en décimal exact ; jamais de prix par défaut (422 `TARIFF_UNAVAILABLE`) ; l'estimation publique ne révèle aucune tranche | `pricing.spec.ts`, `calculator.spec.ts` |
| Logistique | Droits vérifiés **par entrepôt et par agence** (un responsable d'un entrepôt ne voit ni ne modifie les lots, emplacements ou colis d'un autre : 403/404) ; une portée de rôle doit désigner un objet existant de la même entreprise ; chargement et départ de lot contrôlés côté serveur ET en base (index unique partiel, déclencheurs) ; scans idempotents et sûrs sous concurrence (verrou consultatif, verrous de ligne) ; historiques (mouvements, événements de lot) en ajout seul | `warehouse-ops.spec.ts`, `shipments.spec.ts` |
| Manifestes | Téléchargement authentifié et limité au périmètre ; `attachment` + `nosniff` + `no-store` ; **cellules CSV protégées contre l'injection de formules** (nom du client, contenu…) ; nom de fichier assaini | `shipments.spec.ts` |
| Pièces jointes | Type réel lu dans le contenu (le type annoncé n'est qu'une indication) ; JPEG/PNG/WebP/PDF, 8 Mo, 10 par objet ; PDF à contenu actif (`/JavaScript`, `/Launch`, `/EmbeddedFile`…) refusé ; nom assaini ; clé de stockage construite par le serveur (CHECK en base) ; accès vérifié selon le propriétaire (client : ses objets ; personnel : portée d'entrepôt) ; liens HMAC de 5 minutes liés à l'entreprise ; contenu servi avec `nosniff` et CSP `sandbox` | `files.spec.ts` |
| Finance | Montants en décimal exact (jamais de flottant) ; **facture immuable après émission** et numéro sans trou attribués en transaction ; un colis ne peut être facturé qu'une fois (contrainte unique) ; paiement plafonné au dû par verrou de la facture **et** déclencheur différé en base ; reçus, avoirs, remboursements en ajout seul ; **Idempotency-Key** sur l'encaissement en espèces (rejeu sans doublon, clé réutilisée avec un autre contenu refusée) ; droits par agence pour la caisse ; un client ne voit que ses factures émises (pas les brouillons) et une facture d'autrui est un 404 ; export CSV réservé (`payment:export`) | `finance.spec.ts` |
| Webhook de paiement | Inexistant (404) tant que `PAYMENT_WEBHOOK_PROVIDER` / `PAYMENT_WEBHOOK_SECRET` (≥ 32 caractères) ne sont pas définis ; signature HMAC-SHA256 sur `t.corps-brut` comparée en temps constant, tolérance 5 min, **rejeu sans effet** (contrainte unique par événement + verrou), montant et devise comparés au paiement attendu (sinon `MISMATCH`, rien n'est confirmé), événements conservés en ajout seul | `webhooks.spec.ts` (émetteur simulé) |
| Notifications | Événement écrit dans la transaction de l'action (outbox) ; variables des modèles limitées à celles de l'événement ; texte brut dans les modèles ; l'e-mail HTML qui en est tiré **échappe toute valeur** (un nom ou un libellé saisi ne peut pas injecter de HTML ; testé dans `mail.spec.ts`) ; retours à la ligne retirés de l'objet des e-mails (injection d'en-têtes) ; l'e-mail ne contient ni mot de passe, ni jeton, ni identifiant interne ; la raison interne d'une retenue n'est pas envoyée au client ; déduplication par clé | `notifications.spec.ts` |
| Remise au client | Code à 6 chiffres généré **par le client**, montré une fois, conservé sous forme d'**empreinte HMAC** (jamais en clair) ; comparaison en temps constant ; **5 essais erronés → verrou** (comptés même si l'opération échoue), validité 72 h, 5 codes par colis et par heure ; pièce d'identité réduite à son type et ses **4 derniers caractères** ; bénéficiaire contrôlé (actif, dates, pièce) ; remise **bloquée si solde dû**, dérogation réservée à une permission, motivée et **journalisée** ; tentatives **en ajout seul** | `delivery.spec.ts` |
| Livreur | Voit et traite **uniquement les arrêts de ses tournées** ; tout le reste (tournée, arrêt, colis, remise au comptoir) répond 404 ; aucun montant ni solde dans sa vue ; la remise au comptoir exige de lire et confirmer les livraisons **de l'agence** | `delivery.spec.ts` |
| Réclamations | Un client ne voit que les siennes et jamais les **notes internes** ; messages en ajout seul ; identité de la réclamation figée en base ; colis invoqué = colis du client | `claims.spec.ts` |
| Tableau de bord | Calculé en base par des requêtes sur l'entreprise de l'utilisateur (RLS) ; réservé aux droits portant sur **toute** l'entreprise ; aucune valeur de remplacement | `reports.spec.ts` |
| Double authentification (phase 9) | TOTP (RFC 6238 : SHA-1, 30 s, 6 chiffres, fenêtre ±1 pas) ; secret **chiffré au repos** (AES-256-GCM, clé dérivée par HKDF de `TOTP_ENCRYPTION_KEY`) ; **un code ne sert qu'une fois** (comparaison-échange atomique sur le dernier pas utilisé) ; 10 **codes de secours** à usage unique, conservés sous forme d'empreinte HMAC et montrés une seule fois ; activation et désactivation exigent le mot de passe **et** un code ; la connexion répond `TOTP_REQUIRED` puis `INVALID_TOTP` (même message pour un code faux, rejoué ou périmé), comptée dans le verrouillage du compte ; avec `REQUIRE_STAFF_2FA=true` (obligatoire en production) tout compte du personnel sans second facteur ne peut atteindre que sa page Sécurité (`TOTP_ENROLLMENT_REQUIRED`) et ne peut pas le désactiver | `totp.spec.ts`, `two-factor.spec.ts`, `phase9.test.tsx` |
| Stockage de fichiers S3 (phase 9) | Adaptateur `S3Storage` (`STORAGE_DRIVER=s3`) : clés construites par le serveur et refusées si elles sortent de leur espace ; ne crée jamais de bucket ; erreurs franchement remontées (bucket absent, identifiants refusés) | `s3-storage.spec.ts` (contre SeaweedFS réel) |
| Panel d'administration séparé | Application distincte, sur son propre nom de domaine : **cookies de session distincts** (`b2c_admin_refresh` HttpOnly, `b2c_admin_session`) choisis par l'en-tête `X-Client-App: admin`, de sorte qu'une session client et une session du personnel ne se mélangent jamais dans un navigateur ; nginx : CSP stricte, `X-Frame-Options: DENY`, `X-Robots-Tag: noindex`, `Referrer-Policy: no-referrer`, HSTS ; un **compte client est refusé** et sa session refermée ; liens d'invitation et de réinitialisation du personnel dirigés vers le panel. **Limite** : l'en-tête `X-Client-App` n'est pas une preuve d'identité (n'importe quel client peut l'envoyer) : il choisit seulement le nom des cookies ; l'autorisation reste celle du jeton et des droits côté serveur | `auth.spec.ts`, `admin.test.tsx`, `logistics.spec.ts`, contrôle de fumée |
| Journaux | JSON structuré (pino) ; en-têtes `Authorization`, `Cookie`, `Set-Cookie` masqués ; chaîne de requête non journalisée | configuration |

## Ce qui manque ou reste fragile

_Phase 4 : le cookie `b2c_session` est lisible par JavaScript par conception ; il ne contient aucun secret. Un script malveillant (XSS) pourrait toutefois agir au nom de l'utilisateur tant que la page est ouverte : d'où la CSP stricte._

| Sujet | Détail | Phase prévue |
|---|---|---|
| Double authentification : reste à faire | Fait en phase 9 (voir ci-dessus). Absent : SMS, clé de sécurité matérielle (WebAuthn), **réinitialisation par un administrateur** d'un second facteur perdu (aujourd'hui : codes de secours, sinon intervention en base), liste d'appareils de confiance. L'obligation n'est appliquée que si `REQUIRE_STAFF_2FA=true` ; elle se vérifie à chaque requête (le jeton d'accès de 15 min ne la contourne pas) | 10 |
| Vérification du téléphone | Non implémentée (nécessite un fournisseur SMS) | 7 |
| E-mails d'authentification sans file ni nouvelle tentative | **Levé pour les notifications** (phase 7 : file, nouvelles tentatives, échec visible). Reste vrai pour les e-mails d'inscription, de confirmation et de mot de passe oublié : un échec d'envoi est journalisé mais le message est perdu ; le client doit redemander un lien | 7 (outbox + BullMQ) |
| RLS ≠ protection contre l'exécution de SQL arbitraire | Si un attaquant exécutait du SQL avec le rôle applicatif, il pourrait modifier les paramètres de session. La RLS protège contre un filtre oublié dans le code ; la défense contre l'injection reste les requêtes paramétrées et la revue de code | 9 |
| `TRUST_PROXY` | Doit être `true` uniquement derrière un proxy de confiance qui écrase `X-Forwarded-For` et ne fait confiance qu'à **un** saut. Mal réglé, un client peut falsifier son IP et contourner les limites par IP (le verrouillage par compte, lui, reste efficace). **Vérifié sur la pile de production** (phase 10) : avec nginx en point d'entrée unique, 34 requêtes portant un `X-Forwarded-For` différent à chaque fois sont bien limitées. Un second mandataire devant nginx casserait cette garantie (tous les clients partageraient une adresse) | – |
| Renouvellement concurrent strict | Deux renouvellements simultanés avec le même jeton (double clic, réseau instable) révoquent la session : sûr, mais peut déconnecter un client légitime. Une courte période de grâce pourra être ajoutée | 4 |
| Liste de mots de passe courants | ~50 entrées seulement (non élargie en phase 9 : sans source fiable de liste, on n'en invente pas) ; aucun contrôle contre les fuites publiques | 10 |
| Journal d'audit sans chaînage cryptographique | Immuable pour l'application et le propriétaire des tables (vérifié aussi **après restauration**), mais un superutilisateur PostgreSQL pourrait le tronquer. Prévoir export externe/WORM | 10 |
| Pas de détection de robots à l'inscription | Seule la limitation de débit protège (mesurée en charge : exactement 30 requêtes/min/IP, voir TEST_PLAN) ; un CAPTCHA suppose un prestataire | 10 |
| Contrôle de l'existence des portées | **Levé en phase 6** (`SCOPE_NOT_FOUND`). Reste : la suppression d'un entrepôt ou d'une agence n'existe pas (désactivation seulement), ce qui évite des portées orphelines | – |
| Sauvegardes, rétention, chiffrement au repos | La **restauration de PostgreSQL** est vérifiée (`npm run backup:check`, voir TEST_PLAN) et, en phase 10, la **reconstruction complète après sinistre** de la pile de production (DEPLOYMENT.md § 6) ; planification, chiffrement et copie hors machine ne sont **pas** traités (RISKS.md A3) | hébergement |
| `/docs` | Exposé si `ENABLE_DOCS=true` : `compose.prod.yml` impose `false` (et nginx ne relaie pas `/docs`) ; **vérifié** : 404 sur la pile de production | – |
| Stockage de fichiers | Disque local par défaut (`FILES_DIR`, à sauvegarder avec la base : **le test de restauration ne couvre que PostgreSQL**). Adaptateur S3 écrit et testé **contre SeaweedFS uniquement** (jamais contre AWS S3 ni un autre fournisseur) ; l'écrasement d'un objet existant n'est pas interdit côté S3 (les clés contiennent des uuid générés par le serveur : collision pratiquement impossible, mais non empêchée) ; chiffrement au repos des objets à la charge du stockage ; pas de relecture d'empreinte à la lecture | 10 |
| Code de remise de 6 chiffres | 1 million de combinaisons seulement : la protection repose sur le verrou (5 essais), la limite de 5 codes par colis et par heure (≤ 25 essais par heure et par colis) et la limite de débit par adresse IP. Pas d'alerte en cas de tentatives répétées. Le code n'est jamais envoyé par SMS (aucun prestataire) | 9 |
| Livreur compromis | Un compte de livreur volé peut remettre les colis de **sa** tournée s'il connaît le code du client ; il ne voit aucun autre colis ni montant. Pas de géolocalisation ni de double confirmation | 9 |
| Paiements : validation humaine | Un virement ou paiement mobile n'est confirmé que par un agent (`payment:reconcile`) qui compare avec son relevé : l'outil n'a **aucun moyen de vérifier** le paiement lui-même. La séparation des tâches (celui qui déclare ≠ celui qui valide) est garantie pour le client, pas entre deux agents. Pas de double validation pour les gros montants | 9 |
| Caisse mono-devise | Le montant attendu à la clôture additionne les encaissements sans distinguer les devises : à n'utiliser qu'avec une devise de caisse par agence tant que ce n'est pas corrigé | 8-9 |
| Remboursements | Enregistrés dans la plateforme ; l'argent est rendu **hors plateforme** (aucun prestataire) | 9 |
| Webhook de paiement | Exercé uniquement avec un émetteur simulé par les tests ; à valider avec le prestataire réel (format de ses événements, secret, IP émettrices) avant d'activer `PAYMENT_WEBHOOK_*` | 9 |
| Antivirus | Aucun ; seules la vérification du type réel et l'heuristique PDF existent. Ne pas présenter les fichiers comme « analysés » | 9 |
| `SECURITY DEFINER` | `app_package_company` suppose un propriétaire de fonction qui contourne la RLS : en production comme en développement, `b2c_migrator` est le super-utilisateur du conteneur PostgreSQL. Une base gérée sans super-utilisateur n'a pas été essayée et demanderait de revoir les droits | hébergement |
| Numéros de suivi devinables | 50 bits : l'énumération est limitée par le débit (30/min/IP) mais pas par un compteur global ; surveiller les 404 en production | 9 |

## Revue de la phase 9 (guide : OWASP ASVS niveau 2)

Méthode : parcours des chapitres ASVS pertinents pour cette application (authentification, sessions, contrôle d'accès, validation, cryptographie, erreurs et journaux, données, communications, API, fichiers, configuration), en confrontant chaque exigence au code et aux tests existants. **Ce n'est pas une certification** : aucune exigence n'a été vérifiée par un tiers et aucun test d'intrusion n'a été mené.

- **Écart comblé** : second facteur du personnel (ASVS V2, authentification multifacteur) — voir la ligne « Double authentification ».
- **Dépendances** : `multer` et `js-yaml` (vulnérables) sont forcés vers des versions corrigées par `overrides` dans le `package.json` racine ; l'ajout du client S3 a d'abord introduit des paquets vulnérables (version trop ancienne), résolus en prenant la version courante.
- **Charge et déni de service** : voir TEST_PLAN (aucune erreur serveur sous 50 connexions simultanées ; limite par IP exacte).
- **Restauration** : la copie restaurée garde RLS forcée, politiques, déclencheurs et droits (vérifié par comparaison avec la source et par des requêtes avec le rôle applicatif).
- **Reste ouvert** (voir le tableau ci-dessus) : liste de mots de passe courants, audit sans chaînage, absence de détection de robots, `TRUST_PROXY` et période de grâce du renouvellement de session, antivirus, intégrations de paiement réelles, SMS.
